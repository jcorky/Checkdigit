# Benchmark: the three-million-record path

Recorded runs of the workspace path (`checkdigit/workspace/`) on 2026-09-16 and
2026-09-17. Raw results and generator truth files are in `bench/results/`; the
datasets are regenerated by `workspace.bench` (not committed, 150 MB and up).

| Run | Result file | Verification |
|---|---|---|
| CSV, 3,000,000 records, clean | `r3m_clean.benchmark.json` | `r3m_clean.verify.json` |
| CSV, 3,000,000 records, with a simulated crash and resume | `r3m.benchmark.json` | `r3m.verify.json` |
| EDIFACT, 100 messages, 1,000,000 EQD segments | `r1m_edifact.benchmark.json` | generator truth `fleet_1m_edifact.truth.json` |
| Container XML, 1,000,000 containers, 1,666,668 identifier attributes | `r1m_xml.benchmark.json` | generator truth `fleet_1m_xml.truth.json` |
| Two worker processes, EDIFACT and XML files at once | `r2proc.benchmark.json` | same truth files |
| CSV, 100,000 records (procedure check) | `r100k.benchmark.json` | |

## Reproduce

```bash
cd checkdigit
python3 -m workspace.bench generate --records 3000000 --out ../bench/fleet_3m.csv
python3 -m workspace.bench generate-edi --messages 100 --per-message 10000 --out ../bench/fleet_1m.edi
python3 -m workspace.bench generate-xml --containers 1000000 --out ../bench/fleet_1m.xml
bash ../bench/run_phase_c.sh
python3 -m workspace.bench run --dataset ../bench/fleet_3m.csv --root ../bench/runs/r3m --crash-after 1000000
```

Every generator is seeded (`--seed 20260916`): the same arguments produce the same
bytes, the same category counts and the same expected output hash.

## CSV, three million records, clean run

Dataset: 3,000,000 data rows, 149,937,153 bytes UTF-8, mixed CRLF and LF, quoted fields
with embedded newlines and escaped quotes, accented, CJK and emoji remarks. Generated
categories: 2,549,703 valid, 240,345 wrong check digit, 89,882 changed body (most break
the digit), 29,834 missing, 30,228 junk, 45,065 duplicates with different attributes,
14,943 conflicting duplicates. 345,170 rows are correctable; 2,738,243 distinct
identifiers enter the fleet. The job carried an incremental intent, so memberships were
staged during ingest.

| Step | Result |
|---|---|
| Register source (hash, size, codec sniff, copy into the immutable store) | 0.3 s |
| Ingest and validate (stream, kernel per cell, observations, memberships, findings) | 381.2 s |
| Throughput over that step | 7,870 records/s, 0.38 MiB/s |
| Review page, corrected only (200 rows, 25 consecutive pages) | p50 0.98 ms, p95 1.33 ms |
| Review page, prefix `MSKU` | p50 1.40 ms, p95 1.77 ms |
| Review page, invalid structure | p50 2.54 ms, p95 3.20 ms |
| Review page, unfiltered | p50 0.60 ms, p95 0.91 ms |
| Count of corrected proposals (345,170) | 29 ms |
| Publish the main generation (2,738,243 fleet rows in one transaction) | 5.9 s |
| 200-record incremental delta: ingest and compare against the published fleet | 3.3 s |
| Publish the delta | 0.16 s |
| Approve every corrected proposal through a storage-backed selection (345,170 members frozen with versions and digested) | 10.4 s |
| Interrupted export (fails after 1,000 edits) plus full retry under the same key | 5.8 s |
| Timed export of the corrected file, exceptions CSV, ledger CSV and manifest | 5.2 s |
| Whole run | 423.7 s |
| Peak working set of the benchmark process | 1,081,585,664 bytes (1.0 GiB) |
| Database after the run (`workspace.db`, checkpointed) | 1,867,988,992 bytes |
| Immutable source store | 149,947,146 bytes |
| Artifacts (two full exports) | 369,334,287 bytes |

Scenarios recorded in the same run:

| Scenario | Evidence |
|---|---|
| Cancellation | A second job on the same file was cancelled two seconds after it started; the worker stopped 0.21 s after the request with 90,000 records committed, state `cancelled`. |
| Incremental delta leaves the rest untouched | Effects: added 200, retired 0. After publication 2,738,243 fleet rows still carry the main generation's id and 200 carry the delta's; fleet count 2,738,443. |
| Two publishers cannot both overwrite | Two 50-record generations pinned to the same baseline, published from two threads at once: one `published`, one `BASELINE_CONFLICT`; the fleet grew by 50, not 100. |
| Replay applies once | Re-issuing the winning publish with its operation id answered `replayed: true`. |
| Interrupted export never served | The interrupted build stayed `failed` with no hash; the retry under the same idempotency key produced a `ready` artifact with the timed export's hash. |
| Exported bytes | SHA-256 `0688393590b711208da960f4fe35aa376da75943bc7ffedbce97b6e6436f3a36`, identical to the generator's expected hash, 345,170 edits, 60,062 exceptions. |

Independent verification (`workspace.bench verify`, standard-library CSV reader and the
kernel only): records 3,000,000, valid 2,594,768, corrected 345,170, invalid structure
30,228, missing 29,834, edits 345,170, distinct fleet keys 2,738,243, both output hashes;
all equal to the recorded run.

## CSV, three million records, crash and resume

Same dataset and procedure; the first worker was killed after committing 1,000,000
records and a second worker resumed from the checkpoint once the lease expired. Ingest
took 439.8 s including the re-read of the first million records; every count and both
hashes matched the verifier, so no record was counted twice or skipped. Other steps
were within a few seconds of the clean run (`r3m.benchmark.json`).

## Two worker processes

The EDIFACT and XML files were queued as two jobs and two separate
`python3 -m workspace.runner --exit-when-idle` processes were started against the same
database. Each process claimed one job (the completion audit records two distinct
worker ids), both jobs reached `awaiting_review` with the counts above, wall time
80.4 s for 2,333,334 records (29,018 records/s aggregate). One file is never split
across processes; parallelism is per job.

## What this does and does not show

- The three-million-record requirement is met for a CSV fleet file on one host with
  SQLite: ingest, review, approval, export, publication and a delta all complete with
  verified counts and bytes, with and without a crash in the middle.
- EDIFACT and container XML are proven at one million records each on the same path,
  with generator-computed expected output hashes.
- Ingest is single-threaded Python per job: the kernel, the parser state machine and
  SQLite inserts share one core. The CSV run is slower per record than the format runs
  because it also stages memberships (a second random-order index) for reconciliation.
- The first three-million attempt used SQLite's default 2 MiB page cache and slowed from
  about 20,000 to under 5,000 records per second once the random-order key indexes
  outgrew the cache; the cache was raised to 256 MiB per connection and the runs were
  repeated. The first attempt's figures were not kept because it was stopped early.
- Memory: the process peaks at about 1 GiB on the CSV run, most of it SQLite page cache
  across the connections the benchmark opens (main, crashed worker, race and
  cancellation threads). The streaming readers hold one chunk plus one batch of rows.
- Disk pressure is exercised through the free-space threshold in the test suite (ingest
  and export stop with `RESOURCE_BUDGET_EXCEEDED`); an operating-system out-of-space
  write was not recorded.
- Not recorded: the same runs on a smaller machine, or a file split across workers.
